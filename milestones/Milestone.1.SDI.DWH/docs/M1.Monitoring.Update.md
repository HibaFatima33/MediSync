## Add the new measurements yourself

1. Run the three-task M1 pipeline successfully, then run code/export_pipeline_monitoring.py.
2. In Power BI choose Get data, Text/CSV. Import batch_health.csv, query_activity.csv and query_health.csv from Project.Data.And.Results/results/monitoring.
3. Add cards using batch_health: AttemptedRuns, SuccessfulRuns, FailedRuns and SuccessRatePct. A full ingestion attempt covers the three-source PostgreSQL staging operation, not the whole DAG. SuccessRatePct is already a number from 0 to 100: do not apply a percentage format that multiplies it by 100 again.
4. Add cards from query_health: AttemptedQueries, FailedQueries and ErrorRatePct. Each executed SQL question is one attempt; failed attempts are recorded before the exception is raised.
5. For daily counts use query_activity: DateUTC on the axis and Sum of AttemptedQueries as value. This counts automated pipeline SQL executions, not Power BI interactions.
6. For a filtered error rate use DIVIDE(SUM(query_activity[FailedQueries]), SUM(query_activity[AttemptedQueries])) and format as Percentage. Do not average precomputed rates across unequal groups.
7. Use the same ratio approach for filtered batch rates if you later store multiple summary rows.
8. Refresh and save the PBIX, then take your own updated screenshot.

Logging starts with this update. Historical unlogged attempts are not reconstructed. Empty history has a blank rate, not an assumed 100 percent. Query timing probes in the exporter do not count as pipeline question executions. query_health.csv and query_activity.csv summarize the same events: do not add their counts together.

## M1 Airflow and watcher

Use DAG pharma_phase1 with three tasks: ingest_into_postgres, validate_transform_and_load, execute_three_questions. The M1 API accepts --host and --port, default 127.0.0.1:8765. On WSL NAT use the current Windows gateway address in both API binding and PHARMA_API_URL. Start one API server on that port, not M1 and M2 together.

The watcher uses Ubuntu's Airflow CLI to trigger pharma_phase1. It waits for stable sizes and timestamps, then compares SHA256 content hashes. Touching a file without changing its contents does not request another run. By default startup records a baseline and waits. --initial-load requests one startup run. Failed triggers keep the old accepted hashes so they can retry. A finally delay avoids a tight error loop. A trigger accepted by Airflow is not proof that its tasks succeeded.

Example Ubuntu watcher command, after activating the Airflow environment:

```bash
python "/mnt/d/IDA'26/Project Phase 1/milestones/Milestone.1.SDI.DWH/code/watch_csv_and_trigger_airflow.py" --config "/mnt/d/IDA'26/Project Phase 1/milestones/Milestone.1.SDI.DWH/config/config.json" --dag pharma_phase1
```

Copy the updated M1 DAG into /home/p/airflow/dags/pharma_phase1.py and restart the Windows M1 API before demonstration. A fresh three-task M1 recording is the clearest M1-only demonstration. ## Streaming scope

This is an explicit scope decision, not proof that the project-wide streaming requirement is complete; confirm the phase-specific expectation with the instructor.

## Query optimization

Query 3 filters to hospital pharmacies and aggregates both facts separately by hospital, medicine and month before joining. This reduces join inputs and avoids duplicated demand totals. It uses CTEs, not a persisted materialized summary. Queries select relevant fields and join numeric surrogate keys. Primary keys enforce uniqueness. We have not added a separate analytical index, physical partitioning or materialized view. No unmeasured speed improvement or guaranteed sub-second response is claimed.
